======================================================================
0. EXECUTIVE SUMMARY
======================================================================

PROJECT NAME
Testarossa OS

PROJECT TYPE
A from-scratch educational / hobby operating system for 32-bit x86, written
primarily in freestanding C and NASM assembly, built in WSL2 Ubuntu and run
under QEMU.

CORE GOAL
Build a real, bootable teaching OS with its own kernel and a small,
interactive desktop shell if time permits. The visual identity combines:
- Early-2000s Y2K desktop and internet nostalgia.
- An abandoned-computer / digital-archive mystery atmosphere inspired by
  the broad genre and mood of Lily's World XD.
- Cyber-gothic elegance.
- A spatial-inspired 2D interface using layered floating panels and visual
  depth.

IMPORTANT: The goal is NOT to build a Linux distribution, Windows clone,
full 3D desktop, VR operating system, or production-ready general-purpose
OS. The project should demonstrate real operating-system concepts and
present them through a distinctive original interface.

PROJECT DESCRIPTION FOR THE README / EXAM
"Testarossa OS is a 32-bit x86 educational operating system with a custom
monolithic kernel written in C and NASM. Designed for QEMU, it explores
low-level operating-system concepts while developing an original,
cyber-gothic desktop inspired by early-2000s digital culture, layered
spatial interfaces, and the mystery of exploring a forgotten computer."

======================================================================

- CPU mode: protected mode.

- Languages: freestanding C and NASM assembly.

  obtained through the boot path.
- User mode and processes: stretch goals only.

This is a real OS project because the kernel boots and manages low-level
execution. The desktop is a user-facing system shell, not the kernel itself.

MANDATORY FIRST ACTIONS
1. Inspect the repository and all relevant source files, Makefile,
   linker.ld, boot assembly, headers, and current output.
2. Run the existing `make` build before editing.
3. Run `make run` and observe whether the kernel boots.
4. Identify the current Multiboot version and bootloader contract.
5. Summarize the current state, what is confirmed, and the first failure.
6. Make a known-good checkpoint before risky changes.

DO NOT:
- Rewrite the entire project in one response.
- Delete working code just to match a proposed directory structure.
- Change boot protocols or toolchains without explaining the cost.
- Pretend VGA text memory is a pixel framebuffer.
- Guess a framebuffer address or video mode.
- Enable paging before page tables and fault diagnostics are ready.
- Allocate memory before an allocator exists.
- Use libc or hosted-runtime assumptions in the kernel.
- Claim features that are only mockups or untested code.
- Add complex third-party libraries without a clear need.
- Spend early days on decoration while the kernel is unstable.

IMPLEMENTATION LOOP
For each milestone:
1. State the intended change.
2. Make the smallest coherent change.
3. Compile.
4. Boot in QEMU when applicable.
5. Report the exact commands and results.
6. Fix regressions before adding more features.
7. Keep serial diagnostics and VGA fallback intact.

At the end of each task, report:
- Files changed.
- Features implemented.
- Build command and outcome.
- QEMU test and outcome.
- Known bugs / limitations.
- Next recommended milestone.

COMPILER / LINKER CONSIDERATIONS
Use appropriate freestanding 32-bit flags for the chosen toolchain, such
as -m32, -ffreestanding, -fno-stack-protector, and appropriate no-PIE flags.
Use the custom linker script and correct ELF format. The exact flags must
be verified against the current environment rather than copied blindly.
Provide kernel-owned implementations of memory/string routines if needed.
Avoid floating point, C++ runtime features, exceptions, and normal OS
services. Use explicit-width types where suitable.

7. FOUR-WEEK MILESTONE PLAN
======================================================================

WEEK 1 — BOOT, OUTPUT, INPUT
Goal: a repeatably booting kernel.

Day 1: Baseline audit
- Inspect all relevant files.
- Run build and QEMU.
- Identify first failure and fix it before expanding scope.
Acceptance: make succeeds and serial output proves kernel entry.

Day 2: Boot path
- Confirm Multiboot header, entry symbol, stack setup, linker address,
  CPU mode, and assembly-to-C handoff.
- Add serial startup milestones.
Acceptance: deterministic boot and documented entry path.

Day 3: Output
- Stabilize serial and VGA text output.
- Add simple INFO/WARN/ERROR logging if useful.
Acceptance: useful diagnostics visible and no regressions.

Day 4–5: Interrupt and keyboard foundation
- Set up GDT/IDT and appropriate interrupt stubs.
- Remap/configure legacy PIC if needed.
- Implement IRQ1 and basic PS/2 scancode translation.
- Support printable keys, Enter, and Backspace as time allows.
- Send EOI correctly and keep ISR work short.
Acceptance: keyboard input works without an interrupt storm or frozen VM.

WEEK 2 — TIMER AND MEMORY
Goal: show real low-level OS concepts.

Day 6–7: GDT/IDT and exception diagnostics
- Define kernel code/data descriptors.
- Handle relevant CPU exceptions and log useful diagnostics.
- Validate C/assembly calling conventions.
Acceptance: expected interrupts/exceptions are handled or diagnosed.

Day 8: Timer
- Add a simple timer tick counter.
- Report uptime/ticks without doing complex work inside the ISR.
Acceptance: ticks advance predictably.

Day 9–10: Physical memory manager
- Parse bootloader memory information only if it is available and reliable.
- Reserve kernel, boot information, and occupied memory ranges.
- Implement a basic frame allocator (bitmap or free-frame stack).
- If a limited QEMU-only memory model is necessary, document it honestly.
Acceptance: allocation tests do not return reserved frames.

Day 11–12: Paging and heap, conditional
- Build page tables and required identity mappings.
- Add fault diagnostics before enabling paging.
- Enable paging only after the setup is verified.
- Implement a small heap only after the underlying allocator works.
Acceptance: documented page translations and basic allocator/heap tests.
If this becomes a schedule risk, protect the bootable shell milestone.

WEEK 3 — SHELL AND GRAPHICS FOUNDATION
Goal: a usable command interface and a verified path to graphics.

Day 13–14: Shell
Implement a small command parser with commands that really work:
- help
- clear
- about
- version
- uptime
- mem, only if memory data exists
- echo
- ls/cat only if RAMFS exists
Unsupported commands should explain that they are not implemented.
Acceptance: interactive shell can be demonstrated live in QEMU.

Day 15–16: Framebuffer research and setup
- Inspect current boot protocol and QEMU configuration.
- Verify whether the boot path can provide framebuffer information.
- Do not assume VGA text memory is a framebuffer.
- Prefer a bootloader-provided framebuffer request / documented mechanism.
- If protocol migration is necessary, explain the migration cost and
  preserve a known-good checkpoint first.
Acceptance: kernel validates framebuffer base, width, height, pitch, and
pixel format before drawing anything.

Day 17–18: Drawing primitives
- Pixel, filled rectangle, outline rectangle, line.
- Tiny bitmap font.
- Bounds checks and pitch/pixel-format handling.
Acceptance: screen shows readable text and geometric shapes.

Day 19–21: Testarossa desktop prototype
- Draw the background, top strip, taskbar, navigation rail, central hub,
  and a few panels.
- Implement a simple state model for selected/open panels.
- Keyboard navigation is mandatory.
- Mouse is optional.
Acceptance: desktop really renders in QEMU and opens at least one panel
that displays actual system information.

WEEK 4 — FUNCTIONAL PANELS, STABILITY, SUBMISSION
Goal: one coherent, testable demo.

Day 22–23: Core desktop panels
Priority:
1. About Testarossa — OS name, version, architecture and build details.
2. System Monitor — actual uptime/ticks and truthful memory information.
3. Terminal — same working kernel shell, not a picture of a terminal.
4. Archive / Files — only if RAMFS exists.
Acceptance: at least two panels are functional and use real kernel state.

Day 24: RAMFS if stable
- Small in-memory filesystem with a few built-in read-only files.
- Example original demo files: /readme.txt, /archive/entry01.txt,
  /system/about.txt.
- ls and cat should read those entries if implemented.
- Do not claim persistent disk storage: RAMFS contents reset on reboot.
Acceptance: repeatable file listing and reading.

Day 25: Stability
- Cold boot and repeated boot.
- Keyboard input and shell edge cases.
- Desktop panel opening/closing.
- Invalid commands.
- Keep serial diagnostics.
Acceptance: the same demo works repeatedly without editing source.

Day 26: Documentation
- README with prerequisites, build/run, controls, architecture, features,
  limitations, and screenshots if available.
- Architecture diagram: boot -> assembly entry -> C kernel -> interrupts /
  memory / keyboard -> shell / desktop.
- Explain at least one interrupt path and one memory-management concept.
Acceptance: another student can build and run the project.

Days 27–28: Buffer
- Fix bugs and rehearse the exam demo.
- Polish visuals only if core acceptance tests pass.
- Do not begin major scheduler/user-mode work during the buffer unless
  all mandatory milestones are already complete.

8. GRAPHICAL DESKTOP IMPLEMENTATION DETAILS
======================================================================

The GUI should be original and should be developed in the kernel's
available framebuffer path. Do not use HTML, React, a browser, or an
external desktop application as a substitute for the OS GUI.

First prove:
- A framebuffer is actually provided.
- Base address and memory range are valid.
- Width, height, pitch, and pixel format are known.
- Drawing respects pitch and pixel format.
- Out-of-bounds coordinates are rejected or clipped.
- Serial logs remain usable.

Then implement:
A. Full background.
B. Simple built-in font.
C. Window rectangles, borders, title bars, and buttons.
D. Desktop shell layout.
E. Keyboard navigation and panel state.
F. About and System Monitor with actual data.
G. RAMFS-backed Files / Archive if available.
H. Mouse, draggable windows, sparkles, scanlines, and other effects last.

The first mode should be a resolution actually provided by the boot path.
Do not assume a specific mode or hardcode a framebuffer address.

DESIGN COMPONENTS
- Testarossa logo/wordmark in a custom text style.
- Central spatial hub with Archive, Messages, Journal, System.
- Familiar early-2000s title bars and pixel-like icons.
- Floating panels with subtle depth and violet shadows.
- Cyan focus/selection state.
- Magenta accent details.
- Small decorative sparkles used sparingly.
- Optional ambient static / scanline effect only if inexpensive.
- Keyboard navigation with visible selection state.
- Keep readable contrast and avoid excessive visual clutter.

FUNCTIONALITY VS. PRESENTATION
A panel may use sample fictional content only when the content is clearly
a built-in demo artifact. It must not pretend to show real files, real
messages, network state, or memory statistics that the kernel does not
actually have.
